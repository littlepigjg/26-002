缺陷详情

1. 缺陷基础信息
bug_id：bug-029
bug_category：error

2. 缺陷植入信息
store/store.go 的 NewURLStore / NewAccessLogStore 把文件打开失败这个真实错误用 fmt.Errorf("%s", ErrURLStoreInit) / fmt.Errorf("%s", ErrAccessLogInit) 换成一个不带任何原始原因的通用错误；同时 Save / Append 在底层路径不可用时直接返回 errors.New("storage unavailable") / errors.New("log store not opened")，把之前保存在 initErr 中的具体诊断（比如哪一个路径打不开、因为什么打不开）全部丢弃。service/service.go 进一步在 URLService.Create 中用 fmt.Errorf("invalid create request: %s", err.Error()) 和 strings.Contains(msg, "storage unavailable") 分支，把 store 层已经丢失根因的错误再包成 create failed: storage unavailable；在 RedirectService.HandleRedirect 中用 fmt.Errorf("redirect failed: %s", err.Error()) 把 store 层的 ErrCodeNotFound 等具体错误也压扁成一个通用字符串。整个调用链从 store 构造到 service.Create/HandleRedirect 的错误包装全部用 %s / err.Error() 拼接而不是 %w，导致 errors.Is / errors.As 断链，调用方无法从错误中提取原始诊断信息。

缺陷代码所在文件：store/store.go；service/service.go
缺陷代码所在函数：store/store.go:NewURLStore、(*URLStore).Save、NewAccessLogStore；service/service.go:(*URLService).Create、(*RedirectService).HandleRedirect

3. gold_root_cause（标准根因）
文件：store/store.go；service/service.go，符号：NewURLStore、(*URLStore).Save、NewAccessLogStore、(*URLService).Create、(*RedirectService).HandleRedirect，非缺陷钩子：SetPanicGuard；RawSnapshot；PanicGuardFn——这些是诊断/故障演练 API，缺陷根因不在其中，修复时不得修改/删除，失效机制：store 层在 NewURLStore/NewAccessLogStore 中用 fmt.Errorf("%s", ErrURLStoreInit) / fmt.Errorf("%s", ErrAccessLogInit) 丢弃了底层 os.OpenFile 的原始错误，在 Save/Append 中遇到 pathOK=false 时只返回 "storage unavailable" / "log store not opened" 这种无诊断的字符串，把 initErr 中保存的路径和原因全部丢弃；service 层的 Create 用 %s 拼接 err.Error() 再次把 store 的错误包装成通用字符串，并且针对 "storage unavailable" 分支返回一个只含固定文案的错误，彻底丢失路径和具体原因；HandleRedirect 同样用 %s 把 store 的 ErrCodeNotFound 等具体错误拼成 "redirect failed: ..."。结果是调用方拿到的 err.Error() 只包含通用字样（如 storage unavailable / invalid create request / redirect failed），原始的 no-such-dir / raw_url / code not found 等诊断信息在跨层传递中逐级丢失，错误链断裂。

4. Bugfix 题面（user_query）
我在维护一个短链服务，最近加了一个回归检查脚本，专门断言各个 API 返回的错误里必须带上足够的诊断细节。结果连续好几个用例都挂了，现象挺奇怪的：比如我用 `store.NewURLStore` 传入一个指向不存在目录的文件路径，拿到返回错误的 .Error() 只剩一句 "url store init failed"，连具体是哪条路径都没有；然后我再用返回的 store 调用 `URLService.Create`，故意传一个空白 URL，得到的错误 .Error() 变成 "invalid create request: raw_url is required" 这种还能看的文案，但换个场景——我给 store 一个打不开的路径，再调 Create，返回的错误 .Error() 就只剩 "create failed: storage unavailable"，连原本应该能看到的 "no-such-dir" 之类的路径信息完全不见了。还有个调用场景是 `RedirectService.HandleRedirect` 去查一个根本不存在的 code，错误字符串里只剩下 "redirect failed: code not found"，和我预期的 "redirect failed: <更具体的 not-found 诊断>" 相比也不够清楚。我本来以为只要每一层用 `fmt.Errorf("...: %w", err)` 正确包装，错误里总能透出原始信息，但现在看起来要么是某一层根本没 wrap，要么是有人把 wrap 的结果又 .Error() 了一遍再塞回新的 fmt.Errorf 里，导致整条错误链的根因被吃掉。本地复现的话，我在项目根目录写了一个小脚本：`cfg := config.Default(); cfg.Storage.URLFilePath(filepath.Join(os.TempDir(), "no-such-dir", "data.json")); s, err := store.NewURLStore(cfg); _ = err; svc, _ := service.NewURLService(cfg, s); _, err = svc.Create(context.Background(), &model.CreateReq{RawURL:"https://x.com", CustomCode:"abcd", MaxVisits:0}); fmt.Println(err.Error())`，打印出来的就一个光秃秃的 "create failed: storage unavailable"。修的时候别动公开接口哈，内部实现你们自己看着理顺。

5. Diagnosis 题面（user_query 的 diagnosis 变体）
先别改代码，帮我看看这到底怎么回事。我们团队在给刚上线的短链服务加诊断日志，习惯是把底层返回的 error 完整打出来，方便按路径、按 code 排查。结果发现一个诡异的现象：同样是 `store.NewURLStore` 打开失败，传一个不存在目录下的文件路径进去，返回错误的 .Error() 只有一句通用的初始化失败文案，连具体打不开的是哪条路径都没带；更诡异的是把这个 store 喂给 `service.NewURLService`，再调 `Create` 去保存一条链接，原本应该能从错误里看到底层原因，结果 .Error() 又变成了 "create failed: storage unavailable" 这种通用字符串，连原本 store 里能看到的那些路径关键词也没了。查不存在 code 的场景更奇怪：`RedirectService.HandleRedirect` 调不存在的 code，错误字符串只剩 "redirect failed: code not found"，和我想要的完整 not-found 诊断完全不对。我翻了一遍代码，每层好像都在包错误，但感觉包来包去原始信息反而没了——有的地方返回 fmt.Errorf("...: %s", err.Error())，有的地方直接 errors.New("...")，还有一处专门根据字符串内容把错误改写成另一条固定文案。这种组合我怀疑把整条 error chain 搞断了，errors.Is / errors.As 肯定用不了，连最朴素的 err.Error() 子串检查也抓不到原始诊断。你们帮我顺着调用链看看，从构造 store 到 service 的 Create / HandleRedirect，错误信息到底在哪一步被吃掉了。

a) 操作触发：调用方用 store.NewURLStore 传入指向不存在目录的文件路径，再用 URLService.Create 保存任意合法短链，或者用 RedirectService.HandleRedirect 查询不存在的 code，返回的 error 字符串只剩通用文案（如 "url store init failed" / "create failed: storage unavailable" / "redirect failed: code not found"），完全不带原始 os 错误、路径、或具体 not-found 关键字段名。
b) 代码层面可观测异常：整条错误链断裂——errors.Is / errors.As 拿不到底层的 ErrCodeNotFound / store initErr；对 err.Error() 做子串检查也找不到原本应有的路径片段或字段名（如 "no-such-dir"、"raw_url"、"code not found"）。
