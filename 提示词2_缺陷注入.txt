第一部分：缺陷设计要求
================================================================================

【1. 跨文件复杂度要求】
缺陷必须满足以下所有条件：
(1) 缺陷必须跨文件：缺陷根因与触发路径必须分布在至少 2 个不同的 .go 源文件中，禁止集中在单一文件/单一函数内
(2) 修复必须跨文件：修复该缺陷必须同时修改至少 2 个文件、3 个函数，禁止出现"只改一个文件几行代码即可修复"的单点缺陷
(3) 复杂度适中：缺陷通常涉及 2~4 个文件的协同，无需重构整个模块；也不要硬凑两个互不相关的独立缺陷
(4) 报告中所有"文件/函数"字段必须列出全部涉及的文件与函数（至少 2 个文件，3 个函数）

【2. 缺陷涉及的典型形态】（任选其一或组合）
(1) 跨文件共享状态/资源：文件 A 提供并发不安全的共享状态或资源，文件 B 在并发或生命周期上错误使用，触发竞态/泄漏
(2) 跨文件契约/校验缺失：文件 A 的返回值或边界约定在文件 B 中被忽略或错误假设，导致 panic 或错误结果
(3) 跨文件初始化/清理错位：文件 A 负责初始化/打开，文件 B 负责使用/关闭，二者生命周期不匹配

【3. 修改规模要求】
(1) 缺陷植入必须实际修改缺陷涉及到的全部文件，且这些文件的代码「修改行数」必须多于 60 行
(2) 统计口径：被替换的行只算 1 行（删除 30 行 + 新增 30 行 = 修改 30 行），纯新增行或纯删除行各算 1 行
(3) 注释行、空行、文档注释不计入统计
(4) 缺陷逻辑必须有一定复杂度，禁止出现"只改几行即可"的简单小改动缺陷

【4. 必须涉及的运行时机制】
植入的缺陷需要有难度，必须涉及以下复杂场景之一：
- 并发（竞态）
- Context 超时传递
- 错误传播链
- 系统状态污染
- 崩溃恢复（panic/recover）
- 跨服务数据流

严禁植入以下类型的简单缺陷：纯数据变换（字符串归一化、大小写转换、空白处理、枚举映射、关键字映射、索引计算、边界计算、nil/空值未单独处理等浅层单点错误）。缺陷必须体现多文件之间的运行时交互失效，而非单一文件内的静态数据处理错误。

【5. 并发缺陷专项要求】
如果缺陷为并发类型，必须额外遵守：
(1) verify_cmds 必须带上 -race 并用 -count=N（如 20）反复执行以捕获偶发竞态，绝不能只跑单次普通测试
(2) success_criteria 必须明确写明"go test -race -v -count=N 全部通过且无数据竞争"，并补充高并发压测下无 panic 的确定性验收标准
(3) 如果缺陷建议不是并发类型，不得生成并发缺陷

【6. 测试运行要求】
(1) 测试运行时间不超过 5s
(2) 测试文件只需一个 red_green_test.go 即可判定是否有缺陷
(3) 测试文件必须明确输出是否有缺陷（RED/GREEN），放在项目目录下
(4) 修复前测试结果必须全部为红灯（RED），修复后必须全部为绿灯（GREEN），确保修复前后状态可明确区分，绝不允许出现"修复前就是绿灯"或"修复后还是红灯"的情况

================================================================================
第三部分：纯逻辑修复原则（缺陷设计的生死线）
================================================================================

本项目后续验收采用「盲修复 + 复制测试验收」流程：修复者只能看到 Bugfix 题面，看不到 red_green_test.go、看不到缺陷详情、看不到验收.txt；修复完成后，再将 red_green_test.go 复制到修复后的工程里跑验收。

因此，你设计的缺陷必须满足：**完整修复该缺陷，不需要改动任何对外公共 API 签名**。

具体红线：
(1) 不得出现「修复必须把函数返回值从 1 个改成 2 个」才能修好的缺陷
(2) 不得出现「修复必须新增/删除/重命名结构体导出字段」才能修好的缺陷
(3) 不得出现「修复必须修改构造函数参数列表」才能修好的缺陷
(4) 缺陷必须是函数内部的实现逻辑错误（条件判断写反、panic 处理吞错、锁加错位置、错误传播链断裂等），修复只需改动函数体内部代码行，对外调用面保持不变

设计缺陷时必须先在脑中推演一遍修复路径：修复者只改函数内部若干行实现代码，不动签名，能否把问题合理修好？如果推演出必须改签名，立即推翻本套缺陷方案，重新设计。

【关于"修改行数 ≥ 60 行"与"不改签名"的兼容说明】
这两条要求完全可以兼容——例如在 2~3 个函数里重写 70 行内部处理逻辑（条件分支、错误包装、锁粒度、状态机转换、fallback 分支删除等），但对外签名一个都不动。不要为了凑 60 行去新增导出方法或修改返回值类型，一律用函数内部扩写逻辑的方式解决行数要求。

【纯逻辑修复范围的严格界定】
(1) 不得删除任何已导出的方法/函数/类型——哪怕它们是缺陷植入时才新增的，只要命名符合钩子规范（见第四部分），就属于正常业务/诊断能力，修复后必须完整保留
(2) 不得把 SetPanicGuard / XxxWithGuard / RawSnapshot 等钩子方法"改成默认永远不触发"的空实现来修缺陷——正确的修法是修正上层错误处理逻辑
(3) 判断标准：修复前后，`go doc ./... | grep -E "SetPanicGuard|WithGuard|RawSnapshot|PanicGuardFn"` 输出的条目数和名称必须完全一致

第四部分：测试钩子命名规范
================================================================================

缺陷植入过程中如果新增了钩子方法/类型（用于让 red_green_test.go 能稳定触发缺陷），必须遵守以下命名和语义规范：

(1) 名字必须像正常工程里也会存在的业务/诊断 API，禁止出现：MuHack、InjectBug、TestOnlyXxx、HackXxx、BugXxx、PanicInjector 等一看就知道是临时凑的命名

(2) 推荐命名风格：
    - SetXxxGuard（故障演练钩子）
    - XxxWithGuard（带安全/校验前置的操作变体）
    - RawSnapshot（运维诊断快照）
    - SetFaultInjector、DiagnosticDump 等
    这些在真实系统里（混沌工程、线上诊断工具）完全合理，修复者不会觉得是"缺陷代码"而删掉

(3) 钩子方法/类型本身不能有 bug——它们是工具，缺陷必须在调用钩子的上层逻辑里（比如 singleflight 的 recover 吞了 error、service 层把 error 当成 success 走 fallback）

(4) 修复缺陷时完全不需要修改、删除、重命名这些钩子方法/类型——它们和缺陷根因无关，只是被用来触发缺陷的触发器

---------- A. 缺陷详情报告 ----------

完成缺陷植入后，必须输出以下完整信息，每个子项自成一段：

缺陷 N：【bug_id】【缺陷名称】

1. 缺陷基础信息
bug_id：【xxx-xxx-xxx】
bug_category：【concurrency / nil / slice / error / context / defer / other】

2. 缺陷植入信息
【描述具体的错误代码写法，并说明缺陷如何跨文件协同，例如："文件 A 的 Save 方法未加锁写共享 map，文件 B 的 Submit 方法在锁外修改并复用从 Get 返回的 exam 指针，两者并发触发 map 并发写崩溃"】
明确写出缺陷代码涉及的所有文件名和函数名（至少 2 个文件，与缺陷表格的植入位置一致）。

3. gold_root_cause（标准根因）
必须包含三层信息：文件（可多个） + 符号（可多个，与文件一一对应） + 跨文件失效机制。
【强制追加：非缺陷钩子标注】必须把"用于触发缺陷但本身不是缺陷根因的测试钩子方法/类型"单独列出来，明确标注"非缺陷钩子：符号列表——这些钩子是故障演练/诊断 API，缺陷根因不在其中，修复时不得修改/删除"。
格式参考：
文件：【文件A路径】；【文件B路径】，符号：【文件A的函数/结构体/变量名】；【文件B的函数/结构体/变量名】，非缺陷钩子：【SetPanicGuard；SaveWithGuard；GetWithGuard；IncrementVisitsWithGuard；RawSnapshot；PanicGuardFn】，失效机制：【描述文件A与文件B如何协同导致失效，例如：文件A的 Save 方法未加 sync.RWMutex 写锁，文件B的 Submit 方法在锁外修改并复用 exam 指针后调用 Save，并发提交时同时写同一 map，触发 concurrent map writes panic】
此字段必须可直接复制作为 Diagnosis 任务的判据，失效机制必须体现多文件之间的因果链，同时必须明确告知 Diagnosis/Bugfix 执行方：哪些钩子方法是诊断工具，不要动它们。

4. Bugfix 题面（user_query）——字数不低于 200字
核心要求：修复者仅凭此题面 + 项目源码即可独立完成修复，无需任何额外信息。
【严禁模板化】：禁止使用"实际细节为：..."、"复现细节为：..."、"希望为：..."等格式化、标签化的段落。所有信息必须完全融入自然叙述中，像开发者在论坛或 issue 系统里发的一段口语化求助帖。
必须以真实开发者报障口吻自然展开，像描述一个真实遇到的诡异线上问题或 debug 时发现的奇特现象。叙述中必须（通过具体细节自然体现，而非直接宣称）包含：
  - 操作触发细节,如何操作系统的，出现了什么问题，要求不能出现文件名称，函数名称。
  - 实际发生的现象（贴出完整 panic 堆栈或 error 原文，不省略中间帧；逻辑错误则描述实际返回值与预期的对比，比如"预期存进去的 key 是 'abc'，结果读出来变成了 'ABD'"）
  - 期望行为（自然地说出你原本以为应该发生什么，比如"按理说加载完应该所有请求都成功，结果..."，但是不能用按理说加载完应该所有请求都成功，结果去描述）
  - 本地复现步骤（通过描述你做了什么来自然暴露复现路径，不能写写了一个脚本什么的，就是操作系统的哪里哪里）如何做才能复现问题，要求还是不要出现文件名称，函数名称。
  【运行时机制自检】：写完后必须通读一遍，检查是否通过内容本身的描述（如并发场景、超时错误、panic 堆栈、状态不一致等）让读者能自然推断出缺陷涉及的运行时机制（并发、context 生命周期、错误传播、状态污染、运行时崩溃等），而不需要在题面里点出"这是个并发问题"或"涉及 context"。
  【严禁直接暴露根因与修复路径】：题面中严禁出现以下内容：
  (a) 直接指出缺陷属于哪种运行时机制类型（如"这是一个并发问题"、"涉及 context 生命周期"等）
  (b) 直接指出问题出在哪个文件、哪个方法、哪一行代码
  (c) 直接说明应该如何修改代码（如"应该加锁"、"应该检查 context"、"应该返回副本"等）
  (d) 手把手引导修复步骤（如"第一步改 A 文件的 X 函数，第二步改 B 文件的 Y 函数"）
  题面只负责通过现象描述提供足够线索，修复者必须阅读分析源码后才能定位根因和确定修复方案。题面中的描述应当是"我遇到了什么现象"而非"问题在哪里、怎么修"。
  绝对禁止提及：任何测试文件名、验收.txt、钩子方法名（SetPanicGuard 等）、具体文件路径名
  写完后自检：假设完全不知道此项目，只看这段文字 + 翻源码，能否找到复现入口、看懂错在哪、判断要改哪块逻辑

5. Diagnosis 题面（user_query 的 diagnosis 变体）——字数不低于 150 字

验收测试要求：
1. 验证用例必须实现为 .go 测试文件，放在当前目录下，名称为red_green_test.go（可直接 go test 运行），禁止使用 bash 脚本或 docker run。

4. 判定：go test 失败（缺陷未修复）为 RED（红灯）；go test 通过（缺陷已修复）为 GREEN（绿灯）。
5. 测试文件必须在输出中显式打印判定结果：缺陷存在时打印「RED（红灯，缺陷未修复）」，缺陷修复时打印「GREEN（绿灯，缺陷已修复）」，不能只输出错误信息让人自行判断红绿。
6. 测试文件独立可运行，不依赖外部环境变量。
7. 测试文件必须保存为当前目录下的 red_green_test.go（不要只写在验收.txt 文本里），并直接在本机运行该 go test 命令，把真实运行结果（RED/GREEN + 退出码）写回验收.txt
8. 【测试文件不可变性硬约束】red_green_test.go 一旦写入完成，后续所有修复作业（包括 Diagnosis、Bugfix）一律禁止修改该文件。修复只能修改被测代码（.go 业务/库文件），必须让旧的 red_green_test.go 在不改动任何一行的情况下，由「修复前 RED」变为「修复后 GREEN」。若任何修复作业修改了 red_green_test.go，视为作弊，该次修复记为 0 分。
9. 【修复前编译门禁——Bugfix/Diagnosis 阶段同样必须遵守】无论谁接手修复，在写出任何修复代码之前、在修改了任何一行被测代码之后，都必须先执行 go test -c -o /dev/null . ，确认测试包可以无错编译。如果出现 undefined 字段、返回值数量不匹配等错误，只能修改被测代码以恢复签名，绝不能反过来修改 red_green_test.go 去适配被破坏的 API。
10. 【禁止引入测试包专属可见符号】任何为了让红/绿灯测试通过而在被测类型上新增的仅用于测试的字段或方法（例如 MuHack、TestOnlyFlag、InjectPanic 等），都必须在最终修复版中删除。验收时要求：不得通过 grep -n "MuHack\|TestOnly\|Hack" red_green_test.go 以外的 .go 文件中匹配到任何用途不明的测试钩子名。如果必须保留测试钩子（如本项目的 SetPanicGuard），必须在缺陷植入前已在项目中存在且具备业务/诊断语义，而不是临时凑出来的后门字段。
11. 【修复前后状态明确性硬约束】修复前必须全部为红灯（RED），修复后必须全部为绿灯（GREEN），确保修复前后状态可明确区分。绝不允许出现以下情况：
    (1) 修复前就是绿灯（测试通过）——说明缺陷植入失败
    (2) 修复后还是红灯（测试失败）——说明缺陷无法被修复或修复方案无效
    (3) 修复前后无法通过测试结果清晰区分状态
12. 【测试时间硬约束】测试文件必须在 5 秒内运行完毕，不得包含任何会导致测试超时的操作（如长时间 sleep、大循环迭代等）。
